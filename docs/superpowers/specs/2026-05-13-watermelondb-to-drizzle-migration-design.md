# WatermelonDB → expo-sqlite + Drizzle ORM Migration Design

## Goal

Replace WatermelonDB with `expo-sqlite` + `drizzle-orm` so the Iskotify mobile app runs in Expo Go without a custom native build, while preserving reactive queries, type-safe schema, Supabase sync, and offline-first behavior.

## Architecture

The database layer has three layers:

1. **Storage** — `expo-sqlite` (SQLite file on device, WAL journal mode)
2. **ORM** — `drizzle-orm/expo-sqlite` (type-safe queries, `useLiveQuery` for reactive UI)
3. **Migrations** — `drizzle-kit` generates SQL migration files; `useMigrations` hook runs them on app start

`SQLiteProvider` from `expo-sqlite` wraps the app root. A `DrizzleContext` holds the Drizzle client instance, provided via `useSQLiteContext()`. All screens access the client through `useDb()`.

**Tech Stack:** expo-sqlite (bundled with Expo 52), drizzle-orm, drizzle-kit

## Database Client & Provider

`apps/mobile/db/client.ts` exports `createDrizzleClient(sqliteDb)` which:
1. Calls `PRAGMA journal_mode=WAL`
2. Returns `drizzle(sqliteDb, { schema })`

`apps/mobile/db/index.ts` exports `DrizzleProvider` — a React context provider that:
1. Gets the raw SQLite DB from `useSQLiteContext()`
2. Creates the Drizzle client via `createDrizzleClient`
3. Runs pending migrations via `useMigrations(db, migrations)`
4. Exposes the client via `DrizzleContext`

`apps/mobile/hooks/useDb.ts` exports `useDb()` — returns the Drizzle client from `DrizzleContext`. Throws if called outside `DrizzleProvider`.

**Root layout wrapping order:**
```
SQLiteProvider (databaseName="iskotify.db")
  └── DrizzleProvider
        └── app screens
```

## Reactive Queries

Screens use `useLiveQuery` from `drizzle-orm/expo-sqlite`:

```typescript
const { data: settings } = useLiveQuery(
  db.select().from(userSettings).where(eq(userSettings.id, 1))
)
```

The UI re-renders automatically whenever the `user_settings` table changes. This replaces WatermelonDB's observable queries. Screens that only need a one-time read on mount use a plain `useEffect` with `db.select()`.

## Sync Service

`apps/mobile/services/sync.ts` keeps the same pull-based sync logic:

1. Read `user_settings` where `id = 1`; if `selected_listing_slug` is empty, return early
2. Fetch from Supabase: listings, subjects, topics, flashcards where `updated_at > last_synced_at`
3. Upsert all rows in a single Drizzle transaction using `.insert().onConflictDoUpdate()`
4. Update `last_synced_at = Date.now()` inside the same transaction

The function signature changes from `syncOnLaunch(db: Database)` to `syncOnLaunch(db: DrizzleClient)` where `DrizzleClient` is the inferred return type of `createDrizzleClient`.

**Error handling:** errors are caught and logged; the app continues to function offline if sync fails.

---

## Export Service

`apps/mobile/services/export.ts` reads `user_settings` with a plain Drizzle SELECT, builds the same JSON payload, and shares via `expo-sharing`. The public API (`exportUserData(db)`) is unchanged except the `db` parameter type.

## Screen Changes

### `app/_layout.tsx`
- Removes `DatabaseProvider` import
- Adds `SQLiteProvider` (from `expo-sqlite`) wrapping the entire tree
- Adds `DrizzleProvider` inside `SQLiteProvider`
- Migration loading state: shows splash until `useMigrations` reports `success`
- `syncOnLaunch` now receives the Drizzle client from `useDb()`

### `app/onboarding.tsx`
- Replaces `useDatabase()` with `useDb()`
- Replaces WatermelonDB `coll.find('local')` / `coll.create()` / `db.write()` with Drizzle upsert:
  ```typescript
  await db.insert(userSettings).values({ id: 1, selectedListingSlug: slug, lastSyncedAt: 0 })
    .onConflictDoUpdate({ target: userSettings.id, set: { selectedListingSlug: slug, lastSyncedAt: 0 } })
  ```

### `app/(tabs)/profile.tsx`
- Replaces `useDatabase()` with `useDb()`
- Replaces WatermelonDB find/update with Drizzle UPDATE:
  ```typescript
  await db.update(userSettings).set({ selectedListingSlug: '', lastSyncedAt: 0 }).where(eq(userSettings.id, 1))
  ```

- `@nozbe/watermelondb`

### `babel.config.js`
Remove the decorators plugin entry. WatermelonDB required `@babel/plugin-proposal-decorators` for its `@text`, `@field` decorators. Drizzle uses no decorators.

## Migrations

`drizzle-kit generate` produces `apps/mobile/db/migrations/0000_init.sql` with `CREATE TABLE IF NOT EXISTS` for all six tables plus index statements.

The `DrizzleProvider` runs `useMigrations(rawSqliteDb, migrations)` on mount. On first install it applies `0000_init.sql`. On subsequent launches it skips already-applied migrations. Future schema changes add new numbered migration files — no manual SQL required.
