## Locked architecture decisions (researched)
1. **Web data layer = drizzle-orm/sql-js (sql.js wasm) + IndexedDB persistence — NOT expo-sqlite web.** Expo's web sqlite needs COOP/COEP headers (SharedArrayBuffer) which break Google One Tap in non-credentialless browsers (Safari = our iOS audience). sql.js needs no headers. Drizzle ships an official `drizzle-orm/sql-js` driver with the SAME sync-flavored API our code already runs on in tests (better-sqlite3). Persistence: load db bytes from IndexedDB at boot → `new SQL.Database(bytes)` → after writes, debounced `db.export()` → IndexedDB (also on `visibilitychange` hidden). FTS5: sql.js build may lack FTS5 — CREATE_SQL's FTS blocks + triggers must be wrapped per-statement try/catch on web, and `flashcardRetriever` (+ other FTS consumers) falls back to LIKE-based search when FTS5 unavailable (acceptable: web chat is Gemini-only; retrieval quality slightly lower).
2. **Kuya Baw on web = Gemini BYOK ONLY** (llama.rn impossible). Key storage on web = localStorage wrapper in geminiKey.ts (`Platform.OS === 'web'` branch) + a one-line "stored in this browser" note on the key screen.
3. **Web entry is AUTH-FIRST** (W2): Supabase email/password sign-up+sign-in + Google (One Tap via GIS script + button fallback). Mobile keeps local-first flow.
4. **Deploy = static export → Vercel** (`npx expo export -p web` → `dist`). vercel.json: SPA fallback rewrite to /index.html (expo-router static output has per-route html — use `"rewrites": [{source: "/(.*)", destination: "/$1"}]`? NO — static output serves real files; only need a 404 fallback rewrite to /index.html for client-routed deep links; implementer verifies against the actual dist layout). NO COOP/COEP headers (sql.js doesn't need them).
